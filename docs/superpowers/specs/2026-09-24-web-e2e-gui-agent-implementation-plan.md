## 1. 范围与读者须知

**这份计划不重复设计文档已经讲清楚的"为什么"，只回答"谁在什么时候做什么、做到什么程度算完成"。**
读之前请先读完设计文档，尤其是：

- §2 场景约束与关键前提
- §8.1 阶段 0 的 Go/No-Go 阈值表（本计划 §2、§3 是这张表的任务级展开）
- §4.1 Review 闸门的"有/无 reviewer 两种路径"（本计划 §4 按此分岔）

**本计划的两条硬规则，贯穿全篇：**

1. **不确定项不允许被静默跳过。** 凡设计文档标了"待确认""阈值判断"的地方，
   本计划都给出显式任务和产出物，任务完成 = 阈值判断有了结论，不是"做了就算过"。
2. **阶段 1 的任务顺序服从阶段 0 的结论，不是并行设计好再套。**
   §4 的任务分解在多处写"若…则…"，因为阶段 1 的具体形态（要不要 shadow 分支、
   要不要降级路由检测、CI 触发是否含 dispatch）**取决于阶段 0 §3 的评审结论，
   在阶段 0 结束前无法一次性钉死**。这也是为什么阶段 2 及之后不在本计划范围内——
   阶段 1 自己都有分岔，提前规划阶段 2 只会更快过期。

## 2. 阶段 0：基线盘点任务分解（3–5 人日）

对应设计文档 §8.1 的产出清单（10 项）与 Go/No-Go 阈值表（5 项）。每项任务标"产出物"而非
"做了什么"，因为阶段 0 的价值就是把模糊的"应该没问题"换成一份能拍板的证据。

### 2.1 任务清单

| # | 任务 | 产出物 | 对应设计文档 | 预估工时 |
|---|---|---|---|---|

| T0-10 | 抽样统计视觉/报表导出类用例占比 | `baseline/visual-ratio.md`：在 T0-1 的回归清单里统计占比，不只看 10 条试点 | §8.1 产出 10；阈值表第 5 项 | 0.5 人日 |

**合计约 6 人日**，略高于设计文档"3–5 人日"的原始估计——差异主要来自 T0-6（依赖外部排期，
不是纯执行时间）与 T0-4（试调 API 比看文档慢）。**若时间压力大，T0-8/T0-9/T0-10 可以并行做**
（互不依赖，且都是"确认现状"而非需要试跑的任务），实际占用工作日可能不到 6 天。

### 2.2 任务依赖与顺序

- T0-1 → T0-3（先有全量清单才挑得出有代表性的 10 条）→ T0-4、T0-10
- T0-4 是唯一直接决定"是否启动阶段 1"的任务（阈值表第 1 项），**优先安排**，避免其他任务
  做完了才发现这一条不过关
- T0-6 依赖前端仓 CI owner 的档期，**阶段 0 第一天就发出会议邀请**，不要排到最后才联系
- T0-5、T0-7、T0-8、T0-9、T0-10 互相独立，可并行分配给不同人（若阶段 0 有多人参与）

### 2.3 每项任务的验收标准

**不是"文档写了"就算完成，是"结论明确到可以直接填进 §3 的评审表"才算完成**：

- T0-4：不能写"大概能造"，必须是"10 条中 N 条可直接调 API、M 条需轮询、K 条无 API"的确切数字
- T0-6：不能写"理论上可行"，必须有一次真实触发成功（或明确失败原因）的记录
- T0-7：不能写"人力紧张"，必须是具体数字（如"0.3 FTE，无独立 reviewer"）
- T0-9：不能写"环境应该是隔离的"，必须实际检查是否有其他团队/流程在用同一套环境

## 3. 阶段 0 退出评审（Go / No-Go 会议清单）

阶段 0 结束时开一次评审会，**逐条填这张表，不是讨论"感觉怎么样"**。
表格直接对应设计文档 §8.1 的阈值表，来源任务见 §2。

| # | 阈值项 | 阶段 0 结论（填空） | 判定 | 触发动作 |
|---|---|---|---|---|
| 1 | 10 条试点中无 API 造数条数 | ___ / 10 | ≥3 → **No-Go** / <3 → Go | No-Go：先与后端补造数接口，本计划阶段 1 暂停；Go：进 §4 |
| 2 | 阶段 1 FTE 与 reviewer 情况 | FTE=___，reviewer=[有/无] | 无 reviewer 且 <0.5 FTE → **闸门不可用，需重设计或 No-Go**；否则 Go | 见 §4.2 的两条路径分岔 |
| 3 | 路由配置能否静态解析 | [可静态解析 / 不可，运行时下发] | 不影响 Go/No-Go，但决定 §4 任务形态 | 可解析走 CI 常态检测；不可则走 §4.4 降级方案 |
| 4 | CI 容量是否满足阶段 2/3 规模 | [满足 / 不满足，缺口：___] | 不阻塞阶段 1 启动 | 不满足：记入 §8 交接清单，阶段 2 前必须解决 |
| 5 | 环境隔离现状 | [独立/已隔离 / 共享无隔离] | 共享无隔离 → **阶段 1 通过率不可信**，需先处理 | 见 §4.1 前置任务 T1-0 |
| 6 | 视觉/报表类占比 | ___% | >20% → 记入 §8，阶段 2 提前排 `visual-assert` | 不影响阶段 1 任务形态，仅影响阶段 2 规划输入 |
| 7 | `repository_dispatch` 端到端试跑 | [成功 / 失败，原因：___] | 不阻塞阶段 1 启动 | 失败：CI 分层退化为仅每晚定时，见 §4.3 |

### 3.1 评审会的三种整体结论

- **全绿（阈值1、2均为Go）**：按 §4 默认路径推进阶段 1，§4 中"若…则…"按 3、5、7 的结论选择分支。
- **阈值 1 或 2 触发 No-Go**：阶段 1 不启动。若是阈值 1（数据造不出来），
  下一步是与后端协商造数接口排期，重新评估时间另定；若是阈值 2（闸门结构性不成立），
  下一步是与团队负责人讨论人力/reviewer 补给方案，本计划在有新结论前不适用。
- **阈值 1、2 均 Go，其余项有降级**：这是最常见的预期情况——阶段 1 正常启动，
  但具体任务形态（是否走 shadow 分支、路由检测是否降级、CI 是否含 dispatch 触发）
  按评审结论走 §4 对应分支，**不是所有降级都意味着方案打折**，只是范围收敛到已验证成立的部分。

### 3.2 评审会输出

- 填好的阈值表（存入 `baseline/go-no-go-review.md`）
- 若有降级项：更新本计划 §4 中对应任务的执行分支（不是另写文档，直接编辑 §4）
- 若判定 No-Go：记录原因与预计重新评估时间，本计划挂起

## 4. 阶段 1：最小闭环任务分解（2–3 周，1 人）

前提：§3 评审阈值 1、2 均为 Go。以下按周拆分，每周内的任务顺序基本固定，
但**周与周之间不是严格串行**——比如 Week 2 的脚本固化可以在 Week 1 后段就对已完成的
spec 提前启动，不需要等 10 条 spec 全部写完。

| T1-1 | 建仓库骨架 | 按设计文档 §4.3 目录结构建 `qa-e2e/`：`specs/`、`e2e/`、`skills/`、`knowledge/`、`configs/` 及各自的 `AGENTS.md` 占位 | 只建结构，内容后续任务填 |

| T1-7 | Spec review | 10 条 spec 从 `draft` → `approved` | **走 §4.2 的 Review 闸门分支**（见下） |

### 4.2 Review 闸门分支（决定 Week 1 T1-7 和 Week 2 脚本 review 怎么做）

来自 §3 阈值 2 的结论，二选一，**整个阶段 1 只选一次，不来回切换**：

**分支 A —— 有非作者 reviewer（FTE ≥ 0.5 或有独立 reviewer）：**
- T1-7 及后续所有脚本 PR 走非作者 review 后合入 `main`
- 直接进 Week 2，走 4.3 默认流程

**分支 B —— 无非作者 reviewer（阶段 1 常见情况）：**
- spec 与脚本先进 `shadow` 分支，不合 `main`
- 建立"每周固定抽查 3 条 diff"机制：找团队内任何人（哪怕非测试角色）帮忙看一眼，
  记录发现（哪怕是"没发现问题"也要记录，用于 §1.4 指标 6"每周抽查发现的假绿数"）
- **P0/高风险用例（涉及资金、权限、数据删除）100% 找人 review，不允许自审直接合入**——
  这条例外不受"每周只抽 3 条"限制，10 条试点用例里凡命中这个特征的都要单独找人看
- 阶段 1 结束时的硬验收指标（§6）分母范围限定为 shadow 分支产出，
  非作者 review 覆盖率如实记录（预期为低值甚至 0，**不得虚报**）

### 4.4 Week 3：CI 接入与验收准备

以下三项任务的具体形态取决于 §3 评审结论，**每项先看分支条件再确定做法**：

| # | 任务 | 分支条件 | 做法 |
|---|---|---|---|
| T1-16a | CI 路由漂移检测（常态） | §3 阈值 3 = 可静态解析 | 拉前端仓路由配置，与 `sitemap.md` 做集合比对，接入每次 CI |
| T1-16b | 路由覆盖降级方案 | §3 阈值 3 = 不可静态解析 | 按设计文档 §4.4 降级表实现：菜单树快照定期截取比对 / 关键路由接口契约测试 / e2e 导航路径反推覆盖率，接入发版前而非每次 CI |
| T1-17a | CI 含前端仓 dispatch 触发 | §3 阈值 7 = 端到端试跑成功 | 按 T0-6 已验证的 payload schema 接入，触发范围按 `sitemap.md` 路由→模块映射筛选 |
| T1-17b | CI 仅每晚定时全量 | §3 阈值 7 = 试跑失败/未完成 | 不接 dispatch，CI 只保留夜间定时全量一条触发路径；记入 §8 交接清单，标注重新尝试时间点 |
| T1-18 | `codified` 字段 CI 校验 | 无分支，必做 | 增加一步 CI 检查：每条 `status: codified` spec 的 `codified` 路径存在、唯一匹配、落在 `e2e/` 允许目录内 |
| T1-19 | 建立负向验证/mutation 定期复查机制 | 无分支，必做 | 排一个月度/发版前的复查任务（可以只是一条 CI 定时任务或人工日历提醒），10 条脚本先跑通 1 轮 |
| T1-20 | 单条用例生成成本实测记录 | 无分支，必做 | 记录 T1-12 每条脚本生成消耗的 Token/时间，不估算 |
| T1-21 | 阶段 1 验收数据汇总 | 无分支，必做 | 汇总 §6 全部指标，准备评审材料 |
