## 1. 背景与目标

### 1.1 要解决的问题

从零建设 Web To B 后台的 E2E 自动化。不走"人写选择器 + 人维护脚本"的传统路线，
而是采用**意图层人写、代码层 AI 生成、固化后零 Token 回归**的三层结构。

### 1.2 目标

1. **P0 回归从人工点击变为 CI 自动执行**，人工工时可量化下降。
2. **回归执行不消耗 Token**：LLM 只在首次生成、负向验证、失败归因三处介入。
3. **测试知识跟代码一样管理**：意图、脚本、业务知识全部在仓库内、走 Git review。

### 1.3 非目标

- 不追求取代人工测试。目标是覆盖常规回归（原文档估 70–80%），
  把人力释放到经验性、探索性测试上——那部分才是缺陷的主要来源。
- 不建设通用 GUI Agent。本方案是给 Coding Agent 套一层针对 Web 后台的 Harness。
- 不做多端、多机型、视觉元素定位（见 §3.1 的裁剪表）。

### 1.4 衡量成功的指标（从第一天开始记录）

北极星指标（原五项）：

| # | 指标 | 说明 |
|---|---|---|
| 1 | **整条用例**通过率 | 不是单步通过率。单步 98% 在 20 步用例上实际只有 ~67% |
| 2 | 单条用例生成成本（$） | 实测，不估算 |
| 3 | 人工回归工时 | 对比阶段 0 基线 |
| 4 | 负向验证拦下的假绿数量 | 证明该门槛的价值 |
| 5 | 失败归因分布 | 阶段 2 判断是否开放自愈的原料 |

运营健康指标（新增，盯住"审核闸门"与"假绿检出"这两个最容易空心化的环节）：

| # | 指标 | 说明 |
|---|---|---|
| 6 | **非作者 review 覆盖率** | 分母=本阶段合入 PR 数，分子=reviewer≠author 的 PR 数。阶段 1 仅 1 人力，大概率结构性为低值——**如实记录，不假装达标**；阶段 2（1–2 人）起设门槛，见 §8.2/§8.3 |
| 7 | 负向验证/mutation 样本的**定期**失败率 | 区别于指标 4（固化瞬间一次性拦截）：对已 `codified` 脚本按月/发版前批量重跑负向验证，统计"仍能正确 FAIL"的比例。下降即断言随时间劣化的早期信号，见 §6.2 |

## 2. 场景约束与前提

这些约束决定了方案与原文档的所有差异，**任何一条变化都需要重新评估设计**。

| 维度 | 现状 | 对设计的影响 |
|---|---|---|
| 被测端 | **仅 Web / H5** | DOM 完整 → 砍掉视觉元素定位，成本降一个数量级 |
| 产品形态 | **To B 后台 / 内部系统** | 菜单驱动、UI 稳定 → 固化脚本寿命长，路径图谱价值低 |
| 迭代节奏 | **双周或更慢** | 失败的先验概率里真 bug 占比高 → 默认不自愈（§6.3） |
| 自动化存量 | **几乎从零** | 无遗留脚本包袱；但也无历史数据喂知识库 → 知识库后置 |
| 仓库结构 | **前后端分仓，测试须独立仓** | 失去共置，需要上下文桥接机制（§4.2） |
| 前端仓访问 | **可同时 clone** | 桥接机制 1（多目录工作区）成立，这是关键前提 |
| 造数能力 | **有 API 可调**，部分需轮询、存在跨模块依赖 | 可测性门槛已过，无需阶段零补基建；契约需支持 `waitReady` / `needs`（§7） |
| 资源 | **未定**，需先看方案再申请 | 方案分阶段，每阶段标投入与硬验收指标，供谈资源用 |

### 关键前提（若不成立需回头改设计）

1. **能同时 clone 前端仓** —— 支撑 §4.2 机制 1。若失效，`knowledge/` 负担大幅上升。
2. **造数 API 覆盖试点用例** —— 阶段 0 需验证。若 10 条试点里 3 条以上造不出数据，先补造数。
3. **前端仓 CI 能被测试仓通过 `repository_dispatch` 唤起** —— 支撑 §4.2 机制 2，**这是跨团队依赖，
   不是测试仓单方面能落地的**：需要前端仓 CI 主动加一步 dispatch，即需要前端团队配合改代码。
   阶段 0 退出前必须完成一次端到端试跑（前端仓 PR → 成功唤起测试仓 CI），
   否则机制 2 视为不成立，CI 分层（§6.4）退化为"仅每晚定时全量"，不再依赖 PR 触发。

## 3. 方案选型

### 3.1 选定方案：薄 Harness（原方案 A）

保留原文档三层架构的骨架，裁掉在本场景不产生收益的部件：

| 原文档部件 | 处置 | 理由 |
|---|---|---|
| 三层架构 + 三条约束 | **完整保留** | 纯设计，零成本，是安全带 |
| Code-as-Action + 脚本固化 | **完整保留，核心** | UI 稳定 → 固化寿命长，ROI 最高 |
| 视觉理解 Agent（元素定位） | **砍掉** | Web 有完整 DOM，语义 locator 远比坐标稳 |
| 视觉断言 Agent | **降级为兜底 skill** | 仅用于图表、样式、导出文件 |
| 路径图谱平台 + 周 Review | **降级为手写 `sitemap.md`** | 后台是菜单驱动的树，非 App 复杂动线 |
| L0/L1/L2 三层知识库 | **起步只做 L0 + L1** | 从零开始时 L2 是空的，先建结构=造框架 |
| 错误三分类自愈 | **保留分类，自愈后置** | 见 §6.3，本场景取舍与原文档相反 |
| 造数 skill | **保留并前置** | 已有 API，最快见效 |

### 3.2 落选方案

**方案 B：完整照搬（含 L0/L1/L2、路径图谱、自动沉淀、周 Review）。**
落选原因：从零开始时知识库与图谱初期全为空。原文档 100% 存量路径召回率的背后是多年存量资产
（时间线上 Stage 3 标 2025-10、落地数据是 2026 春节，4 个月做到 12.3w 次执行，
只可能是大量 Stage 1/2 资产托底）。先建这套结构会花 1–2 个月产出一个漂亮但空的框架，
正好撞上原文档自己列的第三个坑："不要为短期指标做工程硬编码"。

**方案 C：只做 AI 辅助写脚本，无运行时 Agent。**
落选原因：本质是 Stage 1.5，用例维护仍全人工。但它是阶段 1 第一周的自然产物，
可作里程碑，不作终局。

### 3.3 选 A 的理由：四个约束互相咬合

1. **To B 后台 + 双周迭代** → UI 稳定 → 固化收益最大化、自愈需求最小化。
   因此"先固化、后自愈"是本场景特有的正确顺序，与原文档（周一版、UI 高频变）相反。
2. **Web 单端** → DOM 定位精确 → 砍掉视觉定位，省掉全方案最大一块复杂度与 Token 成本。
3. **有造数 API** → 可测性门槛已过 → 可直接进最小闭环，无需阶段零补基建。
4. **资源未定** → 必须尽快拿出可见成果 → A 的 2–3 周见效是谈资源的筹码，B 做不到。

**A 能无损长成 B（有限承诺）**：目录结构与 L0/L1/L2 知识库分层一开始就按 B 的形状建，
可增量填内容，不存在推倒重来。**但这条承诺不覆盖路径图谱**——从手写 `sitemap.md`
长成原文档那种带截图、`confidence` 分档、周 Review 变更暂存区的图谱平台，
大概率需要换数据结构（纯文本树 → 带元数据的图结构），是独立的演进项，
届时可能要做 schema 迁移甚至重写，不纳入"无损"范围。

## 4. 架构：独立测试仓与上下文桥接

### 4.1 三层如何落到具体载体

| 层 | 载体 | 谁产出 | Git 策略 |
|---|---|---|---|
| 业务意图层 | `specs/**.md` | **人写** | 必须**非作者** review 才能合入 |
| Agent 探索层 | Claude Code + Playwright MCP + `skills/` | 按需触发，不留产物 | 无 |
| 可执行代码层 | `e2e/**.spec.ts` | AI 生成 | 必须**非作者** review diff 后合入，CI 跑 |

**确定性梯度直接映射为 review 强度** —— 这比把三条约束写在文档里更硬。

**闸门的责任人不能是产出者本人。**
若某阶段只有 1 FTE（例如阶段 1，见 §8.2），"人 review diff"这句话在事实上等于作者自审——
自审挡不住"能跑但断言语义错"的假绿（§9.1 风险 3），闸门形同虚设。因此明确：

1. **有非作者 reviewer 时**：走本节默认流程，非作者 review 后合入 `main`，计入硬验收。
2. **无非作者 reviewer 时（阶段 1 的现实情况）**：
   - 脚本只能先进 `shadow` 分支（CI 单独跑，不合 `main`，不计入 §8.2 硬验收的通过率分母）；
   - 退而求其次的最低闸门：**每周固定抽查 3 条已产出 diff**（找团队内任何人，哪怕是非测试角色）
     + **P0/高风险用例（涉及资金、权限、数据删除）100% 找人 review**，不允许自审直接合入 `main`；
   - 阶段 2 起（1–2 人力）恢复"非作者 review 才能合入"为强制默认，见 §8.3 门槛。
3. 这条规则同样适用于 spec 层（意图层）的 review，因为"竹子" case 证明的正是
   意图层的自我审查一样会漏掉断言边界问题。

### 4.2 仓库关系与上下文桥接

```
frontend-repo/          # 被测对象
backend-repo/           # 造数 API 来源
qa-e2e/                 # 测试仓，独立
```

独立仓在此有正当性：测试仓天然跨前后端（驱动前端 UI、调后端 API 造数），
挂在任何一边都别扭。但它失去了共置带来的"代码 diff 与测试意图在同一上下文"的能力，
需要三条机制补回：

| # | 机制 | 说明 | 补偿程度 |
|---|---|---|---|
| 1 | **本地多目录工作区** | `claude --add-dir ../frontend-repo`，Agent 可直接读前端路由与组件 | 几乎无损 |
| 2 | **CI 侧 diff 传递** | 前端仓 PR 经 `repository_dispatch` 唤起测试仓，payload 带变更文件清单与 PR 号 | 支撑 diff 影响面筛选，**跨团队依赖，见下方待定清单** |
| 3 | **`knowledge/` 显式承载** | 路由表、权限矩阵、接口契约写进仓内（CI 场景读不到前端代码） | 有腐化风险，见 4.4 |

**机制 2 落地前必须与前端仓 CI owner 一起明确以下五项**（缺任一项都不算机制 2 成立）：

| 待定项 | 说明 |
|---|---|
| owner | 谁负责在前端仓 CI 里加这一步 dispatch（测试仓团队没有前端仓 CI 权限） |
| `event_type` | `repository_dispatch` 的事件类型标识，测试仓工作流按此过滤 |
| payload schema | 至少含变更文件清单、PR 号；建议加分支名、commit SHA 供追溯 |
| 鉴权 | 前端仓需要一个有权限触发测试仓 `repository_dispatch` 的 token，如何生成与轮转 |
| 失败回退 | dispatch 失败或超时（前端仓 CI 挂了、token 过期）时，测试仓如何兜底——退化为每晚定时全量，不能让"漏跑"静默发生 |

阶段 0 退出前必须完成一次**端到端试跑**（见 §2 关键前提 3），不能只停留在"文档写了这个机制"的层面。

### 4.3 目录结构

```
qa-e2e/
├── AGENTS.md                    # L0 摘要（≤200 行）：做什么、当前覆盖、怎么起步
├── specs/                       # 【意图层】人写 · 强 review
│   ├── AGENTS.md                # L1 路由：模块 → spec 索引
│   ├── conventions.md           # ★ 意图 + 断言写作规范（§5）
│   └── <module>/TC-xxx-<name>.md
├── e2e/                         # 【代码层】AI 生成 · 人 review · CI 跑
│   ├── <module>/TC-xxx.spec.ts
│   └── fixtures/
│       ├── seed/                # 造数 fixture（确定性代码）
│       └── auth.ts              # 角色登录态
├── skills/                      # 【探索层能力】
│   ├── seed-data/SKILL.md       # 自动生成，不手写
│   ├── auth-as/
│   ├── visual-assert/           # 兜底视觉断言
│   └── error-triage/            # 失败三分类（只出报告）
├── knowledge/
│   ├── AGENTS.md                # L1 路由
│   ├── sitemap.md               # 路由 + 菜单路径 + 进入所需权限
│   ├── domain.md                # 术语 / 状态机 / 角色权限矩阵
│   ├── api-contracts.md         # 造数与断言涉及的后端接口契约
│   └── memory/YYYY-MM.md        # 碎片记忆，Agent 自主维护，不 review
└── configs/
    ├── environments.md
    └── upstream.md              # 前后端仓地址、分支对应、版本策略
```

**设计要点：**

1. **`specs/` 与 `e2e/` 一一对应但物理分离。** 意图可先于代码存在：
   先写 spec → review 通过 → 才允许 Agent 生成脚本。让"意图确认前置"成为流程强制。
2. **`AGENTS.md` 只放三处**（根、`specs/`、`knowledge/`）。原文档每目录一份是因为规模大；
   从零开始过早铺开就是造框架。加到第三层目录时再加。
3. **`conventions.md` 是唯一必须人精心写的文件**（§5）。

### 4.4 已知缺陷：`knowledge/` 的副本腐化

`sitemap.md` 里的路由表和权限矩阵是前端代码的副本，副本必然漂移。
前端加了页面没人更新，Agent 就基于过期地图生成用例。

**对策（部分解决）：CI 路由表漂移检测。** 拉前端仓路由配置，与 `sitemap.md` 的路由清单做集合比对，
出现差集即 fail 并提示更新。这能挡住最常见最致命的一类（页面增删）。

**前提尚未验证：这套对策要求路由可静态解析**（路由文件 / 构建产物 / sitemap 接口）。
若前端路由是运行时按权限动态下发菜单（后台系统常见），没有编译期可读的路由清单，
上述比对无法实现。阶段 0 必须确认路由配置形态（§8.1），并按结论二选一：

| 路由形态 | 检测方式 |
|---|---|
| 可静态解析（路由文件/构建产物/sitemap 接口） | 本节的集合比对，进 CI 常态 |
| 仅运行时动态下发、不可静态解析 | **降级方案**：① `sitemap.md` 改为菜单树快照（人工/半自动定期截取当前菜单结构存档对比）；② 关键路由补接口契约测试（命中权限接口返回的菜单项与预期集合比对）；③ e2e 用例的实际导航路径反推覆盖率（跑过的用例覆盖了哪些菜单项，与 sitemap 比对缺口）。三者组合替代编译期检测，检测频率降为发版前而非每次 CI |

阶段 1 硬产出（§8.2）据此改为"路由覆盖清单 + 漂移检测可行性结论"，
而不是无条件承诺"CI 路由漂移检测"这一具体实现。

**未解决：`domain.md` 的语义腐化。** 目前只能靠"改需求时顺手更新"的约定 + 定期人工过一遍。
本方案不假装解决了这一点。用例规模超过 100 条后需重新评估是否应合仓。

**通用原则：能从代码派生的，绝不手写第二份。**
`SKILL.md` 由 fixture 的 `describe` 字段自动生成；`sitemap.md` 是不得不留的副本，故配漂移检测。

## 5. 意图层：spec 格式与断言规范

本节是断言可靠性的真正瓶颈所在。原文档 p27 那个"竹子"失败 case
（页面标题为「竹子」、配图是玉簪，模型判定不符）的根因不是模型能力不足，
而是**用例没有定义断言边界** —— 该断言标题文案，还是断言图文一致性？

### 5.1 spec 文件格式

```markdown
---
id: TC-014
title: 待审批单据通过后从待办消失并出现在已办
priority: P0
module: approval
roles: [approver]              # 需要的登录态角色
seed: [pending-invoice]        # 需要的造数 fixture
status: approved               # draft → approved → codified
codified: e2e/approval/TC-014.spec.ts
visual: false                  # 是否需要 LLM 视觉断言
---

## 前置条件
- 以 `approver` 角色登录
- 存在一张状态为「待审批」的单据，其单号记为 `$INVOICE_NO`

## 操作步骤
1. 进入【财务】→【待我审批】
2. 找到单号为 `$INVOICE_NO` 的行
3. 点击该行的「通过」按钮
4. 在确认弹窗填写审批意见「同意」，点击「确认」

## 预期结果
1. 出现成功提示，文案**包含**「审批成功」
2. 「待我审批」列表中**不存在**单号为 `$INVOICE_NO` 的行
3. 切到「已办」标签后**存在**该行，且其「状态」列文案**等于**「已通过」

## 不检查
- 审批意见是否正确落库（属接口测试范围）
- 列表分页与排序行为（见 TC-021）
```

### 5.2 三处格式设计的用意

**`status` 把"意图确认前置"变成可查询的状态机。**
`draft` 不许生成脚本；`approved` 才允许 Agent 动手；`codified` 表示已有脚本在 CI 跑。
CI 可直接检查"是否存在 `approved` 但未 `codified` 的积压"。

**「不检查」段落是本方案新增（原文档无），直接针对"竹子" case。**
显式写出排除项，比任何提示词工程都有效。

**`$INVOICE_NO` 变量约定防止固化脚本被数据写死。**
若意图层写字面量 `INV-2026-0001`，换环境即碎 —— 数据就是 To B 场景下的"坐标"，
等价于原文档固化脚本里硬存坐标的问题。

**`codified` 字段是索引，不是真相源，需要 CI 校验防腐化。**
`codified: e2e/approval/TC-014.spec.ts` 本身是路径字符串，是脚本文件的一份副本记录，
脚本被移动或改名后这个字段会悄悄失真，且没有任何机制发现——
这与 `sitemap.md` 是同一类"副本必然漂移"问题（§4.4），只是没被列进去。
**对策：CI 增加一步校验**——检查每条 `status: codified` spec 的 `codified` 路径是否存在、
是否唯一匹配、是否落在 `e2e/` 允许目录内；脚本被移动/改名后该校验会 fail，
强制同步更新 `codified` 字段，而不是让它静默腐化。真相源始终是文件系统与测试发现结果，
`codified` 只是为了让人和 Agent 快速定位而缓存的索引。

### 5.3 断言写作规范（七条）

| # | 规则 | ❌ | ✅ |
|---|---|---|---|
| 1 | 必须指明"看哪里" | 页面显示正确 | 表格第 2 行「状态」列文案等于「已通过」 |
| 2 | 区分等于 / 包含 | 提示「审批成功」 | 提示文案**包含**「审批成功」 |
| 3 | 一条断言一个命题 | 列表消失且已办出现 | 拆成两条 |
| 4 | 不用视觉描述业务事实 | 按钮变灰 | 「提交」按钮为 `disabled` |
| 5 | 必须写「不检查」 | （省略） | 显式列出排除项 |
| 6 | 数据用变量不用字面量 | `INV-2026-0001` | `$INVOICE_NO` |
| 7 | 不用模糊时序词 | 稍等后 | 等待列表 loading 消失后 |

### 5.4 断言三档与成本控制

| 档 | 断言类型 | 实现 | Token |
|---|---|---|---|
| 1 | DOM 可判定：文案、存在性、属性、数量 | Playwright `expect` + 语义 locator | **0** |
| 2 | 结构化数据：列表内容、接口响应 | 拦截响应或读表格 DOM | **0** |
| 3 | 视觉：图表、样式、导出文件 | `visual-assert` skill（LLM） | 有 |

**硬规则：默认强制用 1/2 档。用第 3 档必须在 frontmatter 标 `visual: true`
并在「不检查」里说明为什么 DOM 判不了。**

这一条同时控制两件事：Token 成本，以及"假绿"风险 ——
LLM 断言比 DOM 断言更容易给出似是而非的 PASS，因此让它成为需要理由的例外而非默认。

预估 To B 后台 **90%+ 的断言落在第 1/2 档**，第 3 档主要是报表图表与 Excel 导出。

## 6. 执行闭环与失败处理

### 6.1 主流程

```
spec（status: approved）
      │ 人触发（本地 Claude Code，挂载前端仓）
      ▼
Agent 探索执行 ──── 读 spec + knowledge/ + 前端仓代码
      │            调 seed-data / auth-as skill 准备环境
      │            Playwright MCP 在真实浏览器里跑一遍
      ├─ 失败 ─→ 报告卡在哪，人判断是意图问题还是产品问题
      ▼ 成功
生成 e2e/<module>/TC-xxx.spec.ts
      ▼
① 连续 3 次通过     ② 负向验证通过
      ▼
提 PR → 人 review diff → 合入，spec 标 status: codified
      ▼
CI 回归（零 Token）
      │
      └─ 失败 → error-triage 出分类报告 → 人决策
```

### 6.2 固化的两道门槛

**门槛①：连续 3 次通过。**
原文档要求"确定性 > 95%"但未给验证方法。本方案定义为：同一份脚本连跑 3 次全绿才准提 PR。

**口径钉死：本方案所有稳定性指标一律指整条用例的通过率，不是单步。**
单步口径在 20 步用例上会把 98% 变成实际约 67%，这个混淆不能自己踩进去。

**门槛②：负向验证（原文档无，本方案新增）。**
固化前做一次反向检查：故意破坏前置条件（例如造一张**已审批**的单据而非待审批），
确认脚本会 **FAIL**。若破坏前提后脚本仍 PASS，说明断言未真正生效 —— 即"假绿"，
CI 里一堆 PASS 但断言的是错的东西。

成本：每条脚本固化时多跑一次，一次性开销，不进 CI 常态。
**这是本方案对原文档最重要的一处补强** —— 原文档完全没有假绿检出机制。

**负向验证按用例类型分四类构造，不是所有用例都能用"状态反转"这一种手法。**
原示例（审批通过后消失）只覆盖状态反转类，To B 后台还有大量只读/计算/权限类用例
构造不出对称的反向状态，逐一定义构造方式：

| 用例类型 | 负向验证构造方式 | 示例 |
|---|---|---|
| 状态反转类 | 破坏前置状态，断言应变 FAIL | 原示例：造已审批单据而非待审批 |
| 只读/展示类 | 注入一条已知错误/不一致的数据，断言应检测出差异 | 报表页本应显示 A，故意造出 B，断言应 FAIL |
| 计算/聚合类 | 变异输入或注入边界值，断言应能识别计算错误 | 总价字段本应等于单价×数量，故意造不一致数据 |
| 权限类 | 用降权/越权账号跑同一操作，断言应变为"拒绝"或"隐藏" | approver 换成普通角色，「通过」按钮应不可见 |

**确实无法构造负向验证的用例，必须显式豁免，不能默认跳过。**
在 spec frontmatter 加 `negativeVerification: not-applicable` 并在「不检查」段落写明理由，
该豁免进人工 review（对齐 §5.4 `visual: true` 的"例外需理由"设计），
避免"构造不出来就悄悄不做"变成事实上的默认状态。

**局限：这只挡住固化瞬间的假绿，挡不住固化后的断言劣化。**
脚本合入半年后，若有人改了公共 helper 或 locator 导致断言实质失效（例如误改成恒真判断），
不会有任何机制重新触发负向验证去发现它——CI 常态回归只会看到持续 PASS。

**对策：定期批量复跑负向验证（mutation 复查）+ 变更触发 + 禁止软断言。**

1. **定期复跑**：按月或发版前，抽样（或全量，视规模）对已 `codified` 的脚本重新执行一次
   上表对应的负向验证手法，确认仍能正确 FAIL。失败率上升即断言劣化的早期信号，
   计入 §1.4 指标 7。成本可控：复用固化时写好的破坏手法，只是重新触发，不需要重新设计。
2. **变更触发复查**：公共 `helper` / 语义 `locator` 定义变更的 PR，CI 自动关联触发
   所有依赖该 helper/locator 的用例的负向验证复查，而不是等到下一个月度周期——
   这类变更是断言劣化最常见的诱因（一个 helper 改坏，牵连所有用它的脚本）。
3. **关键路径禁止无意义断言和软断言滥用**：P0 用例的断言 review 时额外检查——
   断言目标是否存在（不能断言一个恒真表达式）、是否用了 `soft assert` 但从不检查
   soft 断言是否真的被收集上报（Playwright 的 `expect.soft` 若不配合最终检查会静默通过）。

三者组合仍不构成"证明"，只是把假绿从"完全不可见"变成"有信号可追"，
这条风险的真实兜底强度要等阶段 2 积累数据后重新评估（见 §9.1 风险 3）。

### 6.3 失败处理：默认不自愈（与原文档的主动偏离）

原文档的自愈闭环是为**周一版、UI 高频变**的场景设计：失败的先验概率里"脚本碎了"占多数，
自动重试期望收益高。

**本场景相反。** To B 后台双周迭代、UI 稳定 → 失败的先验概率里**真 bug 占比高**
→ 自动重试收益低、掩盖真 bug 风险高。而错误分类器的准确率是整个自愈闭环的命门，
原文档未披露任何数据。**在分类器准确率未知的前提下让它有权自动重试掉失败，
等于拿真 bug 的漏出去赌。**

| 失败类型 | 判定信号 | 处置 |
|---|---|---|
| **环境错误** | HTTP 5xx、登录态过期、`SeedTimeoutError` 等**明确信号** | ✅ 允许自动重试（最多 1 次） |
| **执行错误** | 选择器未命中、超时 | ❌ 不自动重试，标记待修，人决定 |
| **用例错误** | 断言与产品预期不符 | ❌ 回到 spec 层改意图，走 review |
| **疑似 bug** | 以上都不匹配 | ❌ 直接报出 |

`error-triage` skill **只出分类建议报告，不执行自动动作**。
唯一例外是环境错误的重试 —— 它有确定性信号，且重试不会掩盖真 bug。

这不是保守，而是**把自愈推迟到有数据之后再开**：
阶段 2 累积 200+ 次真实失败样本后算出分类准确率，再决定放开哪一类（§8.3）。

### 6.4 CI 分层

| 触发 | 范围 | 说明 |
|---|---|---|
| 前端仓 PR（`repository_dispatch` 带 diff） | 受影响模块 | 按 `sitemap.md` 的路由→模块映射筛选；**依赖 §4.2 机制 2 端到端试跑通过**，若阶段 0 未跑通则本行不生效，全量回归仅靠下一行兜底 |
| 每晚定时 | 全量 | 机制 2 不成立时的**唯一**触发来源，需确保覆盖 |
| 发版前 | 全量 + P0 重跑 | |
| 每次 CI（若路由可静态解析） | 路由表漂移检测 | §4.4 的守卫；若路由不可静态解析，改为发版前跑降级方案（菜单树快照/契约测试/导航反推） |

### 6.5 Token 成本边界

只有三个动作消耗 Token：**首次生成**、**负向验证**、**triage 报告**，
外加少数 `visual: true` 的用例。

**硬规则：CI 常态回归禁止调 LLM。** 例外仅 `visual: true` 用例与失败后的 triage 报告，两者均低频。

因此月度 Token 成本 ≈ 新增用例数 × 单条生成单价，**可预测、可预算** ——
这也是谈资源时最有说服力的一条。

**这条预测的前提是视觉/报表导出类用例占比不高（§5.4 预估 <10% 落第 3 档）。**
阶段 0 需按 §8.1 阈值表第 5 项抽样确认：若实际占比 >20%，`visual-assert` 提前到阶段 2，
上面这个"月度 Token 成本可预测"的结论要重新算——视觉断言按用例调用、非零且频次不低，
占比被低估会让这条经济学卖点在阶段 2 谈资源时被数据打脸。

## 7. 造数与环境

### 7.1 核心约束：造数必须是确定性代码，不能是 LLM 能力

Agent 探索时与 CI 固化回归时**必须调同一份造数代码**。
若造数是 LLM 现场调 API 拼出来的，固化脚本无法复现同一前置状态 —— 闭环断裂，
表现为"探索时跑通、固化后跑不通"。

因此分成两半：

```
skills/seed-data/SKILL.md     # 给 Agent 读：有哪些 fixture、各造什么（索引）
e2e/fixtures/seed/*.ts        # 确定性代码：真正调后端 API（Agent 与 CI 共用）
```

`SKILL.md` 由 fixture 的 `describe` 字段**自动生成，不手写** —— 否则又是一份会腐化的副本。

### 7.2 fixture 契约

```ts
// e2e/fixtures/seed/approved-contract.ts
export const approvedContract = {
  name: 'approved-contract',
  describe: '创建一份已审批通过的合同，返回 { CONTRACT_NO }',
  requires: ['approver'],                    // 用哪个角色的凭证去造
  needs: ['customer', 'product-sku'],        // ★ 依赖的其他 fixture
  scope: 'test',                             // test（默认）| run
  readyTimeout: 30_000,                      // ★ 就绪轮询超时阈值

  async create(ctx, deps)      { … },        // 发起创建，返回 vars
  async waitReady(ctx, vars)   { … },        // ★ 轮询至真正可用
  async cleanup(ctx, vars)     { … },        // 作废或删除
}
```

- `describe` 给 Agent 读，也是 `SKILL.md` 的生成源
- `create` 的返回值即 spec 里的 `$CONTRACT_NO`，与 §5.2 的变量约定闭环
- spec frontmatter 的 `seed: [approved-contract]` 对应 `name`

### 7.3 异步就绪：`waitReady` 三条规则

1. **轮询业务就绪信号，禁止 `sleep`。** 与 §5.3 规则 7 同源 ——
   固定等待要么不够（偶发失败）要么过长（全量回归超窗口）。
2. **就绪判定优先查后端 API，而非刷 UI 看。** 查接口快、稳、语义明确；
   刷 UI 慢且脆，还会把造数失败伪装成 UI 问题。
3. **超时必须抛专门错误类型 `SeedTimeoutError`。**
   造数轮询超时是最容易被误判成产品 bug 的一类失败；有专门类型，
   §6.3 的 triage 就能确定性归类为环境错误，不靠猜。

### 7.4 跨模块依赖：`needs` 与拓扑排序

Runner 按拓扑序 `create` + `waitReady`，**按反拓扑序 `cleanup`**
（否则先删客户会导致合同删不掉）。**循环依赖在启动时静态检测报错**，不等运行时。

用声明式而非在 `create` 里手工造依赖，换来三件事：

1. **Agent 只需在 spec 写 `seed: [approved-contract]`**，无需知道背后三层依赖 ——
   复杂度封在 fixture 层。
2. **cleanup 顺序自动正确**，不靠人记。
3. **可共享**（见 7.5）。

**依赖图不另写副本：`needs` 字段本身就是那张图的机器可读版本**，
`SKILL.md` 生成时把依赖拓扑一并渲染，Agent 读 skill 即知全貌。
与 §4.4 "能从代码派生的绝不手写第二份"同一原则。

### 7.5 数据隔离与 `scope`

| 做法 | 评价 |
|---|---|
| 每条用例造自己的数据 + **run-id 唯一标识** | ✅ 采用 |
| 共享种子数据，用例只读 | ❌ 一条用例改状态即污染其他用例 |
| 每次重置数据库 | ❌ 慢；共享测试环境做不到 |

造出的数据带 run-id 前缀（如 `E2E-{runId}-0001`），三个收益：用例互不干扰、
**可并行**、出问题能按 run-id 全量清理。

并行是关键 —— 它决定全量回归能否在夜间窗口内跑完。数据不隔离只能串行，
串行到 200 条用例时会超出可用窗口。

| scope | 行为 | 用于 |
|---|---|---|
| `test`（默认） | 每条用例独立造 | 用例会修改的数据 |
| `run` | 整个 run 共享一份 | 用例**只读**的慢速基础数据（客户、SKU、组织架构） |

**硬规则：只有用例不修改的数据才允许 `scope: 'run'`。**
滥用会悄悄破坏隔离设计 —— 两条用例改同一份数据，失败会变成偶发且极难查。

`scope: 'run'` 的 fixture 在并行下会被多 worker 抢造。
**起步阶段不做运行时抢锁**，走 Playwright `globalSetup` 在并行开始前串行预置。

**这不是一句配置能带过的，是一个需要自研的小型调度器**，职责包括：
扫描本次运行涉及的所有测试文件、收集各自声明的 `run` 级 fixture 依赖、按 `name` 去重、
按 §7.4 的拓扑规则排序、串行执行 `create` + `waitReady`、把结果注入各 worker 的上下文、
任一预置失败时向所有 worker 传播失败（而不是让 worker 各自超时）、
本次运行内做结果缓存（避免同一个 `run` 级 fixture 被重复读取触发副作用）、
预置失败时的重试策略。**阶段 1 任务分解中必须单列"run-scope 预置调度器"一项独立估点**，
不能把它算进"配环境"这类杂项时间里，否则阶段 1 的排期会系统性偏乐观。
代价是全量回归前多几十秒（调度本身的开销，不含上面这段实现成本）。

`cleanup` 在测试后执行，但**不依赖它保证正确性**：即使 cleanup 失败，
唯一标识也能保证下次运行不受影响。另加每周孤儿数据清理任务，按 run-id 前缀扫。

**前提：本节整套隔离设计假设测试环境不被外部脏写。**
run-id 前缀只能隔离"自己造的数据"，挡不住其他团队/业务线在同一套共享环境上的手工操作
或另一套自动化。若环境是共享的且没有隔离机制或流量探针，通过率下跌可能是环境噪音而非
脚本问题，会污染 §8.2 的通过率数字、误触发 §9.2 退出条件。**阶段 0 必须确认环境隔离现状**
（§8.1 阈值表第 4 项）：共享且无隔离/无探针 → 先做环境隔离或给自动化流量打标分流，
再信任阶段 1 的通过率。

### 7.6 登录态

`auth-as` skill 用 Playwright `storageState`：每角色登录一次、存 JSON、后续复用；
带过期检测（请求 401 即重登一次）。

避免每条用例走一遍登录 UI —— 那是最慢也最易碎的一段，且除专门测登录的用例外它不是被测目标。

### 7.7 环境

`configs/environments.md` + `.env`，两套起步：
**local**（本地前端 + staging 后端）、**staging**（全 staging）。
凭据走环境变量与 CI secret，不进仓。

造数 API 故障属 §6.3 的**环境错误** —— 有明确信号（HTTP 5xx / `SeedTimeoutError`），
允许自动重试 1 次，之后 fail 并明确报"环境问题，非产品 bug"。

### 7.8 风险：依赖深度

链越长，造数耗时越长、环境错误概率越高。
**运营约束：依赖深度超过 3 层即停下评估**，是否应让后端提供组合造数接口
（一次调用直接产出终态数据）。

这属于可测性建设，需与后端团队协商并**提前进排期** ——
不能等到写用例时才发现缺接口。

## 8. 分阶段落地与验收标准

资源未定，故每阶段标清**投入、产出、硬验收指标、决策点**。
决策点既是谈资源的依据，也是该停就停的地方。

### 8.1 阶段 0：基线盘点（3–5 人日，先于一切）

不做这步，后面所有"提效"都无法证明。

**产出：**
1. 每版必跑的回归用例清单
2. **一轮人工回归的实际人时**（找人真实记一次工时，不估算）
3. 挑出 10 条 P0 试点用例
4. 这 10 条的 fixture 可行性盘点：哪些能直接调 API、哪些需轮询、
   哪些是深层依赖、**哪些根本没有 API**
5. **前端仓路由配置的具体形式**（解析路由文件 / 读构建产物 / 读 sitemap 接口）——
   决定 §4.4 路由漂移检测能否按阶段 1 排期的方式实现（原列为待澄清项 3，
   因其是阶段 1 硬验收指标的可行性前提，前置到阶段 0 一并确认，避免时序倒挂）
6. **`repository_dispatch` 端到端试跑结果**（§2 关键前提 3、§4.2 机制 2）——
   与前端仓 CI owner 对齐 owner / event_type / payload schema / 鉴权 / 失败回退五项后，
   实际跑通一次前端仓 PR 唤起测试仓 CI；跑不通则确定阶段 1 CI 分层退化为"仅每晚定时"
7. **阶段 1 是否有非作者 reviewer，团队实际可投入 FTE**（§4.1）——决定阶段 1 走
   "默认流程"还是"重设计 / No-Go"，见下方阈值表第 2 项
8. **CI 平台容量与可用夜间窗口时长**——按阶段 2/3 的用例规模（60–80 条、200+ 累积样本）
   反推所需并行度，与实际可用窗口对比，见下方阈值表第 3 项
9. **测试环境是否共享、是否有隔离机制或探针**——决定 run-id 隔离（§7.5）是否够用，
   见下方阈值表第 4 项
10. **视觉 / 报表导出类用例的实际占比**——抽样统计 10 条试点用例之外的更大范围回归清单，
    见下方阈值表第 5 项

**Go / No-Go 阈值表（新增，五项待确认项全部升级为有判据的决策点，不再是"找时间弄清楚"）：**

| # | 待确认项 | 阈值 | 触发后动作 |
|---|---|---|---|
| 1 | 10 条试点用例中，需人工准备数据（无 API / 无法自动造数）的条数 | **≥ 3/10** | **No-Go**：先与后端补造数接口，不启动阶段 1（原有决策点，阈值对齐至此表） |
| 2 | 阶段 1 是否有独立 reviewer；团队实际可投入 FTE | **无独立 reviewer 且 < 0.5 FTE** | **review 闸门不可用**：§4.1 的"shadow 分支 + 每周抽查"退而求其次方案本身也需要"找人抽查"的最低人力，< 0.5 FTE 下这个最低要求也满足不了 → **需重新设计闸门机制（如引入外部/兼职 reviewer）或直接 No-Go**，不能带着一个连退而求其次都不成立的闸门进入阶段 1 |
| 3 | CI 平台容量（并发数、夜间窗口时长）能否支撑阶段 2（60–80 条）/ 阶段 3（200+ 累积样本）规模 | **容量不满足阶段 2/3 的推算需求** | **不阻塞阶段 1**：阶段 1 规模小（10 条），容量问题不会在阶段 1 暴露。**但阶段 1 只验证功能闭环，不验证容量**——阶段 2 启动前必须解决容量问题（扩容或重新设计并行策略），否则阶段 2 的"6–8 周扩到 60–80 条"排期会在容量瓶颈处停滞 |
| 4 | 测试环境是否与其他团队 / 业务线共享；是否有隔离机制或流量探针区分自动化流量 | **共享环境且无隔离机制、无探针** | **阶段 1 通过率不可信**：run-id 前缀只隔离"自己造的数据"，挡不住外部脏写；通过率下跌可能是环境噪音而非脚本问题，会误触发 §9.2 退出条件。**动作：先做环境隔离（独立测试环境/命名空间）或加噪音分流（给自动化流量打标，故障定位时先排除非自动化来源）**，之后才能信任阶段 1 的通过率数字 |
| 5 | 视觉 / 报表导出类用例占比 | **> 20%** | §5.4 预估的"90%+ 断言落 1/2 档"不成立，**`visual-assert` skill 从阶段 3 提前到阶段 2**（§8.3 产出需相应调整）；同步**重估 §6.5 的 Token 成本预测**——视觉断言是仅次于首次生成的 Token 消耗点，占比被低估会让"月度 Token 成本可预测"这条经济学卖点站不住 |

**决策点（原有，阈值见上表第 1 项）：若 10 条里有 3 条以上造不出数据 → 先与后端补造数接口，不启动阶段 1。**
数据造不出来还硬上，只会做出一堆靠手工前置的伪自动化。

**决策点（新增·路由）：若路由配置无法静态解析**（例如权限接口运行时动态下发菜单，
无编译期路由文件可读）**→ 路由漂移检测降级为 §4.4 的降级方案，不再作为阶段 1 硬验收指标**，
需在阶段 1 启动前更新 §8.2 的验收表，不能带着一条实现不了的硬指标进入阶段 1。

**决策点（新增·CI 桥接）：若端到端试跑未在阶段 0 内跑通 → 阶段 1 硬产出去掉
"前端仓 dispatch 触发"，只保留"夜间全量"**，且需在待澄清项里记录重新尝试的时间点，
不能带着一个未验证成立的跨团队机制进入阶段 1 排期。

**决策点（新增·Review 闸门，阈值见上表第 2 项）：**
- 若有独立 reviewer 或 FTE ≥ 0.5：走 §4.1"默认流程"或"shadow 分支退而求其次"方案，
  阶段 1 硬验收指标的"整条用例通过率"分母范围限定为 shadow 分支产出（§8.2 已调整）。
- **若无独立 reviewer 且 FTE < 0.5：不进入阶段 1，先解决闸门机制问题。**
  这与"决策点（原有）"性质不同——不是"数据造不出来"，而是"闸门本身在结构上不成立"，
  没有闸门的固化等于把假绿检出全部押注在"负向验证"这一道防线上，风险不可接受。

### 8.2 阶段 1：最小闭环（2–3 周，1 人）

**产出：** 仓库骨架 → `conventions.md` → 10 条 spec（人写）→ 对应 fixture →
run-scope 预置调度器（独立估点，见 §7.5）→ 10 条固化脚本 →
CI（夜间全量必达；前端仓 dispatch 触发依赖 §8.1 决策点 2 的端到端试跑结果，
未跑通则不计入本阶段产出）→ 路由覆盖清单 + 漂移检测可行性结论（依赖 §8.1 决策点 1 的路由形态确认，
可静态解析则实现 CI 常态检测，不可则实现 §4.4 降级方案）→
`codified` 字段存在性/唯一性 CI 校验（§5.2）。

**Review 闸门（依赖 §8.1 决策点 3 的结论，二选一）：**

- **有非作者 reviewer**：所有 spec 与脚本走非作者 review 后合入 `main`，计入下表硬验收。
- **无非作者 reviewer**（阶段 1 常见情况）：脚本先进 `shadow` 分支（§4.1），
  每周固定抽查 3 条 diff + P0/高风险用例 100% 找人 review；
  **下表"整条用例通过率"的分母范围限定为 shadow 分支产出**，不得把作者自审合入 `main`
  的脚本计入正式硬验收——这是防止闸门空心化后还拿着数字去谈资源。

**硬验收指标：**

| 指标 | 门槛 |
|---|---|
| 负向验证通过（含分类构造，见 §6.2） | 10/10 |
| 连续 3 次全绿 | 10/10 |
| CI 连跑 5 个工作日，**整条用例**通过率（分母范围见上方 Review 闸门结论） | ≥ 90%（见下方口径） |
| 单条用例生成成本 | **实测记录**，不估算 |
| 非作者 review 覆盖率 | **如实记录，不设门槛**——若阶段 1 无 reviewer，此项预期为低值甚至 0，
  **如实写 0，不得虚报**；先记基线，阶段 2 起设门槛（§8.3） |
| 每周抽查发现的假绿数 | 建立每周抽查 3 条的机制并记录发现数（新增指标 6，见 §1.4） |
| 负向验证/mutation 定期复查 | 10/10 条脚本纳入复查清单并跑通至少 1 轮（建立机制本身，暂不要求失败率数值） |
| `codified` 校验 | CI 校验上线，10/10 条 spec 的 `codified` 路径通过存在性检查 |

**通过率口径（避免两种读法）：** 分母 = 用例数 × 运行轮次（10 条 × 5 天 = 50 次执行），
分子 = 其中通过的次数，**扣除已判定为环境错误的执行**（环境问题不算脚本不稳定，但要单独统计次数）。
同时附加一条约束：**不允许存在通过率 < 60% 的单条用例** ——
否则 9 条完美 + 1 条全红也能凑出 90%，而那 1 条才是真问题。

通过率起步定 90% 而非 98%：**98% 是有多年存量资产团队的结果，
第一个月拿它当目标只会逼出硬编码**（原文档自列的第三个坑）。

**决策点：拿前四个数字谈资源**（非作者 review 覆盖率、每周抽查、定期复查、`codified` 校验
四项阶段 1 只建机制、记基线，不作为谈资源的筹码）。**若通过率 < 80%，停下查根因，不扩规模**——
碎的东西复制 60 份只会碎 60 份。**若阶段 1 全程无 reviewer 导致所有产出滞留 shadow 分支**，
谈资源时必须如实说明"闭环尚未过人审"，不能把 shadow 分支的绿灯包装成已验证的成果。

### 8.3 阶段 2：规模化到覆盖 P0（6–8 周，1–2 人）

**产出：** 扩到 60–80 条覆盖 P0 回归；开启并行（run-id 隔离已在阶段 1 就位）；
`error-triage` 上线**只出报告**；`memory/` 开始沉淀踩坑记录。

**硬验收指标：**

| 指标 | 门槛 |
|---|---|
| P0 回归人工工时降幅 | 对比阶段 0 基线，**可量化** |
| 整条用例通过率 | ≥ 95%（口径同 §8.2，单条下限提至 80%） |
| 累积失败样本 | ≥ 200 次 |
| 非作者 review 覆盖率 | ≥ 80%（1–2 人力起可结构性满足；低于此值说明 review 在走过场） |
| 每周抽查发现的假绿数 | 建立每周抽查机制并记录发现数——数值本身不设门槛，但**连续两周零发现 + 抽查样本量不足**需人工复核抽查是否流于形式 |
| 负向验证/mutation 定期复查失败率 | 记录趋势，**上升即触发排查**（断言随脚本演化劣化的信号，见 §6.2） |
| `codified` 校验失败次数 | 记录趋势——持续为 0 说明脚本移动/改名有跟着更新字段的习惯；非零则说明副本腐化在发生，需人工过一遍 spec（§5.2） |

**决策点：用 200+ 次失败样本算出 triage 分类器的真实准确率，
再决定是否放开「执行错误自愈」。** §6.3 推迟自愈正是为了等这个数据 ——
有数据后决策才成立。

### 8.4 阶段 3：按需深化（持续，不设结束线）

`domain.md` / L2 详情层补完；报表图表启用视觉断言；新需求的 spec 由 Agent 起草、人 review。

验收看**新需求用例的采纳率**（Agent 起草被人接受的比例）。

**路径图谱放到这里都不一定要做** —— 后台是菜单驱动的树，`sitemap.md` 大概率一直够用。

### 8.5 明确不做（YAGNI）

视觉元素定位、路径图谱平台、周 Review 机制、L2 知识库前置建设、
独立 Skill 包分发、多机型矩阵。

理由统一：**要么被 Web DOM 取代，要么是规模化的产物而非前提。**
从零开始时建这些等于给自己造框架。

## 9. 风险与退出条件

| # | 风险 | 影响 | 对策 | 是否已解决 |

| 9 | **阶段 1 无非作者 reviewer，review 闸门空心化**（新增） | 作者自审等于无闸门，假绿/断言语义错更难被挡住 | Go/No-Go 阈值：无独立 reviewer 且 <0.5 FTE → 不进阶段 1，先重设计闸门；否则走 shadow 分支 + 每周抽查 3 条 + P0 100% review（§4.1、§8.1 阈值表第 2 项） | 🟡 **有明确阈值但结论未知**：≥0.5 FTE 时退而求其次方案可挡一部分（覆盖率仍远低于正常 review）；<0.5 FTE 时判定为 No-Go，不是"部分解决"能兜的问题 |

| 12 | **CI 容量不足以支撑阶段 2/3 规模**（新增） | 阶段 1 用 10 条验证不出容量问题，扩到 60–80 条/200+ 样本时才在容量瓶颈处停滞 | 阶段 0 按阶段 2/3 规模反推容量需求，与实际窗口对比（§8.1 阈值表第 3 项） | ⚠️ **阶段 1 结论不代表阶段 2/3 可行**，容量问题必须在阶段 2 启动前单独解决，不能顺延到阶段 1 通过就默认没问题 |
| 13 | **共享测试环境无隔离/无探针，通过率数字被环境噪音污染**（新增） | 环境噪音导致的失败被误判为脚本不稳定，可能错误触发 §9.2 退出条件（通过率<80%停下查根因） | 阶段 0 确认环境隔离现状，共享无隔离则先隔离或加噪音分流（§7.5、§8.1 阈值表第 4 项） | ⚠️ **未解决**，阶段 0 前默认假设"环境干净"是本方案目前唯一没有验证过的隐藏前提 |

### 9.2 退出条件（必须提前写进方案）

出现以下任一情形，判定该路径当前不可行并停止投入：

1. **阶段 1 结束通过率 < 80% 且根因是产品可测性**（而非脚本问题）
   → 先补可测性，方案本身推迟。
2. **单条用例生成成本 > 人工写脚本成本** → 直接人工写，不用 Agent。
3. **阶段 2 人工工时降幅 < 20%** → 审核负担已吃掉收益（风险 5 成真）。

**不写退出条件的方案，在数据不好时只会被不断加投入抢救。**

### 保留的原文档核心设计

以下部分完整继承，是方案的骨架：

- **三层架构 + 三条约束**（意图不可改、确定性 >95% 才固化、人只深度参与意图层）
- **Code-as-Action 而非 ToolCall** —— 可固化性、调试能力、表达力、成本四项占优
- **脚本固化 → 零 Token 回归** —— 整套方案的经济学基础
- **知识跟代码一起管理**（Git、review、分支、diff）
- **人定标准、Agent 执行探索** —— 组织原则
- **错误三分类**（环境 / 执行 / 用例）—— 保留分类，仅推迟自动化处置
