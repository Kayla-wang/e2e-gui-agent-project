- **状态**：待评审

## 1. 背景与目标

### 1.1 要解决的问题

从零建设 Web To B 后台的 E2E 自动化。不走"人写选择器 + 人维护脚本"的传统路线，
而是采用**意图层人写、代码层 AI 生成、固化后零 Token 回归**的三层结构。

### 1.2 目标

1. **P0 回归从人工点击变为 CI 自动执行**，人工工时可量化下降。
2. **回归执行不消耗 Token**：LLM 只在首次生成、负向验证、失败归因三处介入。
3. **测试知识跟代码一样管理**：意图、脚本、业务知识全部在仓库内、走 Git review。

### 1.3 非目标

- 不追求取代人工测试。目标是覆盖常规回归（原文档估 70–80%），
  把人力释放到经验性、探索性测试上——那部分才是缺陷的主要来源。
- 不建设通用 GUI Agent。本方案是给 Coding Agent 套一层针对 Web 后台的 Harness。
- 不做多端、多机型、视觉元素定位（见 §3.1 的裁剪表）。

### 1.4 衡量成功的五个指标（从第一天开始记录）

| # | 指标 | 说明 |
|---|---|---|
| 1 | **整条用例**通过率 | 不是单步通过率。单步 98% 在 20 步用例上实际只有 ~67% |
| 2 | 单条用例生成成本（$） | 实测，不估算 |
| 3 | 人工回归工时 | 对比阶段 0 基线 |
| 4 | 负向验证拦下的假绿数量 | 证明该门槛的价值 |
| 5 | 失败归因分布 | 阶段 2 判断是否开放自愈的原料 |

## 2. 场景约束与前提

这些约束决定了方案与原文档的所有差异，**任何一条变化都需要重新评估设计**。

| 维度 | 现状 | 对设计的影响 |
|---|---|---|
| 被测端 | **仅 Web / H5** | DOM 完整 → 砍掉视觉元素定位，成本降一个数量级 |
| 产品形态 | **To B 后台 / 内部系统** | 菜单驱动、UI 稳定 → 固化脚本寿命长，路径图谱价值低 |
| 迭代节奏 | **双周或更慢** | 失败的先验概率里真 bug 占比高 → 默认不自愈（§6.3） |
| 自动化存量 | **几乎从零** | 无遗留脚本包袱；但也无历史数据喂知识库 → 知识库后置 |
| 仓库结构 | **前后端分仓，测试须独立仓** | 失去共置，需要上下文桥接机制（§4.2） |
| 前端仓访问 | **可同时 clone** | 桥接机制 1（多目录工作区）成立，这是关键前提 |
| 造数能力 | **有 API 可调**，部分需轮询、存在跨模块依赖 | 可测性门槛已过，无需阶段零补基建；契约需支持 `waitReady` / `needs`（§7） |
| 资源 | **未定**，需先看方案再申请 | 方案分阶段，每阶段标投入与硬验收指标，供谈资源用 |

### 关键前提（若不成立需回头改设计）

1. **能同时 clone 前端仓** —— 支撑 §4.2 机制 1。若失效，`knowledge/` 负担大幅上升。
2. **造数 API 覆盖试点用例** —— 阶段 0 需验证。若 10 条试点里 3 条以上造不出数据，先补造数。

## 3. 方案选型

### 3.1 选定方案：薄 Harness（原方案 A）

保留原文档三层架构的骨架，裁掉在本场景不产生收益的部件：

| 原文档部件 | 处置 | 理由 |
|---|---|---|
| 三层架构 + 三条约束 | **完整保留** | 纯设计，零成本，是安全带 |
| Code-as-Action + 脚本固化 | **完整保留，核心** | UI 稳定 → 固化寿命长，ROI 最高 |
| 视觉理解 Agent（元素定位） | **砍掉** | Web 有完整 DOM，语义 locator 远比坐标稳 |
| 视觉断言 Agent | **降级为兜底 skill** | 仅用于图表、样式、导出文件 |
| 路径图谱平台 + 周 Review | **降级为手写 `sitemap.md`** | 后台是菜单驱动的树，非 App 复杂动线 |
| L0/L1/L2 三层知识库 | **起步只做 L0 + L1** | 从零开始时 L2 是空的，先建结构=造框架 |
| 错误三分类自愈 | **保留分类，自愈后置** | 见 §6.3，本场景取舍与原文档相反 |
| 造数 skill | **保留并前置** | 已有 API，最快见效 |

### 3.2 落选方案

**方案 B：完整照搬（含 L0/L1/L2、路径图谱、自动沉淀、周 Review）。**
落选原因：从零开始时知识库与图谱初期全为空。原文档 100% 存量路径召回率的背后是多年存量资产
（时间线上 Stage 3 标 2025-10、落地数据是 2026 春节，4 个月做到 12.3w 次执行，
只可能是大量 Stage 1/2 资产托底）。先建这套结构会花 1–2 个月产出一个漂亮但空的框架，
正好撞上原文档自己列的第三个坑："不要为短期指标做工程硬编码"。

**方案 C：只做 AI 辅助写脚本，无运行时 Agent。**
落选原因：本质是 Stage 1.5，用例维护仍全人工。但它是阶段 1 第一周的自然产物，
可作里程碑，不作终局。

### 3.3 选 A 的理由：四个约束互相咬合

1. **To B 后台 + 双周迭代** → UI 稳定 → 固化收益最大化、自愈需求最小化。
   因此"先固化、后自愈"是本场景特有的正确顺序，与原文档（周一版、UI 高频变）相反。
2. **Web 单端** → DOM 定位精确 → 砍掉视觉定位，省掉全方案最大一块复杂度与 Token 成本。
3. **有造数 API** → 可测性门槛已过 → 可直接进最小闭环，无需阶段零补基建。
4. **资源未定** → 必须尽快拿出可见成果 → A 的 2–3 周见效是谈资源的筹码，B 做不到。

**A 能无损长成 B**：目录结构一开始就按 B 的形状建，知识库只是增量填内容，不存在推倒重来。

## 4. 架构：独立测试仓与上下文桥接

### 4.1 三层如何落到具体载体

| 层 | 载体 | 谁产出 | Git 策略 |
|---|---|---|---|
| 业务意图层 | `specs/**.md` | **人写** | 必须人 review 才能合入 |
| Agent 探索层 | Claude Code + Playwright MCP + `skills/` | 按需触发，不留产物 | 无 |
| 可执行代码层 | `e2e/**.spec.ts` | AI 生成 | 人 review diff 后合入，CI 跑 |

**确定性梯度直接映射为 review 强度** —— 这比把三条约束写在文档里更硬。

### 4.2 仓库关系与上下文桥接

```
frontend-repo/          # 被测对象
backend-repo/           # 造数 API 来源
qa-e2e/                 # 测试仓，独立
```

独立仓在此有正当性：测试仓天然跨前后端（驱动前端 UI、调后端 API 造数），
挂在任何一边都别扭。但它失去了共置带来的"代码 diff 与测试意图在同一上下文"的能力，
需要三条机制补回：

| # | 机制 | 说明 | 补偿程度 |
|---|---|---|---|
| 1 | **本地多目录工作区** | `claude --add-dir ../frontend-repo`，Agent 可直接读前端路由与组件 | 几乎无损 |
| 2 | **CI 侧 diff 传递** | 前端仓 PR 经 `repository_dispatch` 唤起测试仓，payload 带变更文件清单与 PR 号 | 支撑 diff 影响面筛选 |
| 3 | **`knowledge/` 显式承载** | 路由表、权限矩阵、接口契约写进仓内（CI 场景读不到前端代码） | 有腐化风险，见 4.4 |

### 4.3 目录结构

```
qa-e2e/
├── AGENTS.md                    # L0 摘要（≤200 行）：做什么、当前覆盖、怎么起步
├── specs/                       # 【意图层】人写 · 强 review
│   ├── AGENTS.md                # L1 路由：模块 → spec 索引
│   ├── conventions.md           # ★ 意图 + 断言写作规范（§5）
│   └── <module>/TC-xxx-<name>.md
├── e2e/                         # 【代码层】AI 生成 · 人 review · CI 跑
│   ├── <module>/TC-xxx.spec.ts
│   └── fixtures/
│       ├── seed/                # 造数 fixture（确定性代码）
│       └── auth.ts              # 角色登录态
├── skills/                      # 【探索层能力】
│   ├── seed-data/SKILL.md       # 自动生成，不手写
│   ├── auth-as/
│   ├── visual-assert/           # 兜底视觉断言
│   └── error-triage/            # 失败三分类（只出报告）
├── knowledge/
│   ├── AGENTS.md                # L1 路由
│   ├── sitemap.md               # 路由 + 菜单路径 + 进入所需权限
│   ├── domain.md                # 术语 / 状态机 / 角色权限矩阵
│   ├── api-contracts.md         # 造数与断言涉及的后端接口契约
│   └── memory/YYYY-MM.md        # 碎片记忆，Agent 自主维护，不 review
└── configs/
    ├── environments.md
    └── upstream.md              # 前后端仓地址、分支对应、版本策略
```

**设计要点：**

1. **`specs/` 与 `e2e/` 一一对应但物理分离。** 意图可先于代码存在：
   先写 spec → review 通过 → 才允许 Agent 生成脚本。让"意图确认前置"成为流程强制。
2. **`AGENTS.md` 只放三处**（根、`specs/`、`knowledge/`）。原文档每目录一份是因为规模大；
   从零开始过早铺开就是造框架。加到第三层目录时再加。
3. **`conventions.md` 是唯一必须人精心写的文件**（§5）。

### 4.4 已知缺陷：`knowledge/` 的副本腐化

`sitemap.md` 里的路由表和权限矩阵是前端代码的副本，副本必然漂移。
前端加了页面没人更新，Agent 就基于过期地图生成用例。

**对策（部分解决）：CI 路由表漂移检测。** 拉前端仓路由配置，与 `sitemap.md` 的路由清单做集合比对，
出现差集即 fail 并提示更新。这能挡住最常见最致命的一类（页面增删）。

**未解决：`domain.md` 的语义腐化。** 目前只能靠"改需求时顺手更新"的约定 + 定期人工过一遍。
本方案不假装解决了这一点。用例规模超过 100 条后需重新评估是否应合仓。

**通用原则：能从代码派生的，绝不手写第二份。**
`SKILL.md` 由 fixture 的 `describe` 字段自动生成；`sitemap.md` 是不得不留的副本，故配漂移检测。

## 5. 意图层：spec 格式与断言规范

本节是断言可靠性的真正瓶颈所在。原文档 p27 那个"竹子"失败 case
（页面标题为「竹子」、配图是玉簪，模型判定不符）的根因不是模型能力不足，
而是**用例没有定义断言边界** —— 该断言标题文案，还是断言图文一致性？

### 5.1 spec 文件格式

```markdown
---
id: TC-014
title: 待审批单据通过后从待办消失并出现在已办
priority: P0
module: approval
roles: [approver]              # 需要的登录态角色
seed: [pending-invoice]        # 需要的造数 fixture
status: approved               # draft → approved → codified
codified: e2e/approval/TC-014.spec.ts
visual: false                  # 是否需要 LLM 视觉断言
---

## 前置条件
- 以 `approver` 角色登录
- 存在一张状态为「待审批」的单据，其单号记为 `$INVOICE_NO`

## 操作步骤
1. 进入【财务】→【待我审批】
2. 找到单号为 `$INVOICE_NO` 的行
3. 点击该行的「通过」按钮
4. 在确认弹窗填写审批意见「同意」，点击「确认」

## 预期结果
1. 出现成功提示，文案**包含**「审批成功」
2. 「待我审批」列表中**不存在**单号为 `$INVOICE_NO` 的行
3. 切到「已办」标签后**存在**该行，且其「状态」列文案**等于**「已通过」

## 不检查
- 审批意见是否正确落库（属接口测试范围）
- 列表分页与排序行为（见 TC-021）
```

### 5.2 三处格式设计的用意

**`status` 把"意图确认前置"变成可查询的状态机。**
`draft` 不许生成脚本；`approved` 才允许 Agent 动手；`codified` 表示已有脚本在 CI 跑。
CI 可直接检查"是否存在 `approved` 但未 `codified` 的积压"。

**「不检查」段落是本方案新增（原文档无），直接针对"竹子" case。**
显式写出排除项，比任何提示词工程都有效。

**`$INVOICE_NO` 变量约定防止固化脚本被数据写死。**
若意图层写字面量 `INV-2026-0001`，换环境即碎 —— 数据就是 To B 场景下的"坐标"，
等价于原文档固化脚本里硬存坐标的问题。

### 5.3 断言写作规范（七条）

| # | 规则 | ❌ | ✅ |
|---|---|---|---|
| 1 | 必须指明"看哪里" | 页面显示正确 | 表格第 2 行「状态」列文案等于「已通过」 |
| 2 | 区分等于 / 包含 | 提示「审批成功」 | 提示文案**包含**「审批成功」 |
| 3 | 一条断言一个命题 | 列表消失且已办出现 | 拆成两条 |
| 4 | 不用视觉描述业务事实 | 按钮变灰 | 「提交」按钮为 `disabled` |
| 5 | 必须写「不检查」 | （省略） | 显式列出排除项 |
| 6 | 数据用变量不用字面量 | `INV-2026-0001` | `$INVOICE_NO` |
| 7 | 不用模糊时序词 | 稍等后 | 等待列表 loading 消失后 |

### 5.4 断言三档与成本控制

| 档 | 断言类型 | 实现 | Token |
|---|---|---|---|
| 1 | DOM 可判定：文案、存在性、属性、数量 | Playwright `expect` + 语义 locator | **0** |
| 2 | 结构化数据：列表内容、接口响应 | 拦截响应或读表格 DOM | **0** |
| 3 | 视觉：图表、样式、导出文件 | `visual-assert` skill（LLM） | 有 |

**硬规则：默认强制用 1/2 档。用第 3 档必须在 frontmatter 标 `visual: true`
并在「不检查」里说明为什么 DOM 判不了。**

这一条同时控制两件事：Token 成本，以及"假绿"风险 ——
LLM 断言比 DOM 断言更容易给出似是而非的 PASS，因此让它成为需要理由的例外而非默认。

预估 To B 后台 **90%+ 的断言落在第 1/2 档**，第 3 档主要是报表图表与 Excel 导出。

## 6. 执行闭环与失败处理

### 6.1 主流程

```
spec（status: approved）
      │ 人触发（本地 Claude Code，挂载前端仓）
      ▼
Agent 探索执行 ──── 读 spec + knowledge/ + 前端仓代码
      │            调 seed-data / auth-as skill 准备环境
      │            Playwright MCP 在真实浏览器里跑一遍
      ├─ 失败 ─→ 报告卡在哪，人判断是意图问题还是产品问题
      ▼ 成功
生成 e2e/<module>/TC-xxx.spec.ts
      ▼
① 连续 3 次通过     ② 负向验证通过
      ▼
提 PR → 人 review diff → 合入，spec 标 status: codified
      ▼
CI 回归（零 Token）
      │
      └─ 失败 → error-triage 出分类报告 → 人决策
```

### 6.2 固化的两道门槛

**门槛①：连续 3 次通过。**
原文档要求"确定性 > 95%"但未给验证方法。本方案定义为：同一份脚本连跑 3 次全绿才准提 PR。

**口径钉死：本方案所有稳定性指标一律指整条用例的通过率，不是单步。**
单步口径在 20 步用例上会把 98% 变成实际约 67%，这个混淆不能自己踩进去。

**门槛②：负向验证（原文档无，本方案新增）。**
固化前做一次反向检查：故意破坏前置条件（例如造一张**已审批**的单据而非待审批），
确认脚本会 **FAIL**。若破坏前提后脚本仍 PASS，说明断言未真正生效 —— 即"假绿"，
CI 里一堆 PASS 但断言的是错的东西。

成本：每条脚本固化时多跑一次，一次性开销，不进 CI 常态。
**这是本方案对原文档最重要的一处补强** —— 原文档完全没有假绿检出机制。

### 6.3 失败处理：默认不自愈（与原文档的主动偏离）

原文档的自愈闭环是为**周一版、UI 高频变**的场景设计：失败的先验概率里"脚本碎了"占多数，
自动重试期望收益高。

**本场景相反。** To B 后台双周迭代、UI 稳定 → 失败的先验概率里**真 bug 占比高**
→ 自动重试收益低、掩盖真 bug 风险高。而错误分类器的准确率是整个自愈闭环的命门，
原文档未披露任何数据。**在分类器准确率未知的前提下让它有权自动重试掉失败，
等于拿真 bug 的漏出去赌。**

| 失败类型 | 判定信号 | 处置 |
|---|---|---|
| **环境错误** | HTTP 5xx、登录态过期、`SeedTimeoutError` 等**明确信号** | ✅ 允许自动重试（最多 1 次） |
| **执行错误** | 选择器未命中、超时 | ❌ 不自动重试，标记待修，人决定 |
| **用例错误** | 断言与产品预期不符 | ❌ 回到 spec 层改意图，走 review |
| **疑似 bug** | 以上都不匹配 | ❌ 直接报出 |

`error-triage` skill **只出分类建议报告，不执行自动动作**。
唯一例外是环境错误的重试 —— 它有确定性信号，且重试不会掩盖真 bug。

这不是保守，而是**把自愈推迟到有数据之后再开**：
阶段 2 累积 200+ 次真实失败样本后算出分类准确率，再决定放开哪一类（§8.3）。

### 6.4 CI 分层

| 触发 | 范围 | 说明 |
|---|---|---|
| 前端仓 PR（`repository_dispatch` 带 diff） | 受影响模块 | 按 `sitemap.md` 的路由→模块映射筛选 |
| 每晚定时 | 全量 | |
| 发版前 | 全量 + P0 重跑 | |
| 每次 CI | 路由表漂移检测 | §4.4 的守卫 |

### 6.5 Token 成本边界

只有三个动作消耗 Token：**首次生成**、**负向验证**、**triage 报告**，
外加少数 `visual: true` 的用例。

**硬规则：CI 常态回归禁止调 LLM。** 例外仅 `visual: true` 用例与失败后的 triage 报告，两者均低频。

因此月度 Token 成本 ≈ 新增用例数 × 单条生成单价，**可预测、可预算** ——
这也是谈资源时最有说服力的一条。

## 7. 造数与环境

### 7.1 核心约束：造数必须是确定性代码，不能是 LLM 能力

Agent 探索时与 CI 固化回归时**必须调同一份造数代码**。
若造数是 LLM 现场调 API 拼出来的，固化脚本无法复现同一前置状态 —— 闭环断裂，
表现为"探索时跑通、固化后跑不通"。

因此分成两半：

```
skills/seed-data/SKILL.md     # 给 Agent 读：有哪些 fixture、各造什么（索引）
e2e/fixtures/seed/*.ts        # 确定性代码：真正调后端 API（Agent 与 CI 共用）
```

`SKILL.md` 由 fixture 的 `describe` 字段**自动生成，不手写** —— 否则又是一份会腐化的副本。

### 7.2 fixture 契约

```ts
// e2e/fixtures/seed/approved-contract.ts
export const approvedContract = {
  name: 'approved-contract',
  describe: '创建一份已审批通过的合同，返回 { CONTRACT_NO }',
  requires: ['approver'],                    // 用哪个角色的凭证去造
  needs: ['customer', 'product-sku'],        // ★ 依赖的其他 fixture
  scope: 'test',                             // test（默认）| run
  readyTimeout: 30_000,                      // ★ 就绪轮询超时阈值

  async create(ctx, deps)      { … },        // 发起创建，返回 vars
  async waitReady(ctx, vars)   { … },        // ★ 轮询至真正可用
  async cleanup(ctx, vars)     { … },        // 作废或删除
}
```

- `describe` 给 Agent 读，也是 `SKILL.md` 的生成源
- `create` 的返回值即 spec 里的 `$CONTRACT_NO`，与 §5.2 的变量约定闭环
- spec frontmatter 的 `seed: [approved-contract]` 对应 `name`

### 7.3 异步就绪：`waitReady` 三条规则

1. **轮询业务就绪信号，禁止 `sleep`。** 与 §5.3 规则 7 同源 ——
   固定等待要么不够（偶发失败）要么过长（全量回归超窗口）。
2. **就绪判定优先查后端 API，而非刷 UI 看。** 查接口快、稳、语义明确；
   刷 UI 慢且脆，还会把造数失败伪装成 UI 问题。
3. **超时必须抛专门错误类型 `SeedTimeoutError`。**
   造数轮询超时是最容易被误判成产品 bug 的一类失败；有专门类型，
   §6.3 的 triage 就能确定性归类为环境错误，不靠猜。

### 7.4 跨模块依赖：`needs` 与拓扑排序

Runner 按拓扑序 `create` + `waitReady`，**按反拓扑序 `cleanup`**
（否则先删客户会导致合同删不掉）。**循环依赖在启动时静态检测报错**，不等运行时。

用声明式而非在 `create` 里手工造依赖，换来三件事：

1. **Agent 只需在 spec 写 `seed: [approved-contract]`**，无需知道背后三层依赖 ——
   复杂度封在 fixture 层。
2. **cleanup 顺序自动正确**，不靠人记。
3. **可共享**（见 7.5）。

**依赖图不另写副本：`needs` 字段本身就是那张图的机器可读版本**，
`SKILL.md` 生成时把依赖拓扑一并渲染，Agent 读 skill 即知全貌。
与 §4.4 "能从代码派生的绝不手写第二份"同一原则。

### 7.5 数据隔离与 `scope`

| 做法 | 评价 |
|---|---|
| 每条用例造自己的数据 + **run-id 唯一标识** | ✅ 采用 |
| 共享种子数据，用例只读 | ❌ 一条用例改状态即污染其他用例 |
| 每次重置数据库 | ❌ 慢；共享测试环境做不到 |

造出的数据带 run-id 前缀（如 `E2E-{runId}-0001`），三个收益：用例互不干扰、
**可并行**、出问题能按 run-id 全量清理。

并行是关键 —— 它决定全量回归能否在夜间窗口内跑完。数据不隔离只能串行，
串行到 200 条用例时会超出可用窗口。

| scope | 行为 | 用于 |
|---|---|---|
| `test`（默认） | 每条用例独立造 | 用例会修改的数据 |
| `run` | 整个 run 共享一份 | 用例**只读**的慢速基础数据（客户、SKU、组织架构） |

**硬规则：只有用例不修改的数据才允许 `scope: 'run'`。**
滥用会悄悄破坏隔离设计 —— 两条用例改同一份数据，失败会变成偶发且极难查。

`scope: 'run'` 的 fixture 在并行下会被多 worker 抢造。
**起步阶段不做运行时抢锁**，走 Playwright `globalSetup` 在并行开始前串行预置。
简单可靠，代价是全量回归前多几十秒。

`cleanup` 在测试后执行，但**不依赖它保证正确性**：即使 cleanup 失败，
唯一标识也能保证下次运行不受影响。另加每周孤儿数据清理任务，按 run-id 前缀扫。

### 7.6 登录态

`auth-as` skill 用 Playwright `storageState`：每角色登录一次、存 JSON、后续复用；
带过期检测（请求 401 即重登一次）。

避免每条用例走一遍登录 UI —— 那是最慢也最易碎的一段，且除专门测登录的用例外它不是被测目标。

### 7.7 环境

`configs/environments.md` + `.env`，两套起步：
**local**（本地前端 + staging 后端）、**staging**（全 staging）。
凭据走环境变量与 CI secret，不进仓。

造数 API 故障属 §6.3 的**环境错误** —— 有明确信号（HTTP 5xx / `SeedTimeoutError`），
允许自动重试 1 次，之后 fail 并明确报"环境问题，非产品 bug"。

### 7.8 风险：依赖深度

链越长，造数耗时越长、环境错误概率越高。
**运营约束：依赖深度超过 3 层即停下评估**，是否应让后端提供组合造数接口
（一次调用直接产出终态数据）。

这属于可测性建设，需与后端团队协商并**提前进排期** ——
不能等到写用例时才发现缺接口。

## 8. 分阶段落地与验收标准

资源未定，故每阶段标清**投入、产出、硬验收指标、决策点**。
决策点既是谈资源的依据，也是该停就停的地方。

### 8.1 阶段 0：基线盘点（3–5 人日，先于一切）

不做这步，后面所有"提效"都无法证明。

**产出：**
1. 每版必跑的回归用例清单
2. **一轮人工回归的实际人时**（找人真实记一次工时，不估算）
3. 挑出 10 条 P0 试点用例
4. 这 10 条的 fixture 可行性盘点：哪些能直接调 API、哪些需轮询、
   哪些是深层依赖、**哪些根本没有 API**

**决策点：若 10 条里有 3 条以上造不出数据 → 先与后端补造数接口，不启动阶段 1。**
数据造不出来还硬上，只会做出一堆靠手工前置的伪自动化。

### 8.2 阶段 1：最小闭环（2–3 周，1 人）

**产出：** 仓库骨架 → `conventions.md` → 10 条 spec（人写）→ 对应 fixture →
10 条固化脚本 → CI（夜间全量 + 前端仓 dispatch）+ 路由漂移检测。

**硬验收指标：**

| 指标 | 门槛 |
|---|---|
| 负向验证通过 | 10/10 |
| 连续 3 次全绿 | 10/10 |
| CI 连跑 5 个工作日，**整条用例**通过率 | ≥ 90%（见下方口径） |
| 单条用例生成成本 | **实测记录**，不估算 |

**通过率口径（避免两种读法）：** 分母 = 用例数 × 运行轮次（10 条 × 5 天 = 50 次执行），
分子 = 其中通过的次数，**扣除已判定为环境错误的执行**（环境问题不算脚本不稳定，但要单独统计次数）。
同时附加一条约束：**不允许存在通过率 < 60% 的单条用例** ——
否则 9 条完美 + 1 条全红也能凑出 90%，而那 1 条才是真问题。

通过率起步定 90% 而非 98%：**98% 是有多年存量资产团队的结果，
第一个月拿它当目标只会逼出硬编码**（原文档自列的第三个坑）。

**决策点：拿这四个数字谈资源。若通过率 < 80%，停下查根因，不扩规模** ——
碎的东西复制 60 份只会碎 60 份。

### 8.3 阶段 2：规模化到覆盖 P0（6–8 周，1–2 人）

**产出：** 扩到 60–80 条覆盖 P0 回归；开启并行（run-id 隔离已在阶段 1 就位）；
`error-triage` 上线**只出报告**；`memory/` 开始沉淀踩坑记录。

**硬验收指标：**

| 指标 | 门槛 |
|---|---|
| P0 回归人工工时降幅 | 对比阶段 0 基线，**可量化** |
| 整条用例通过率 | ≥ 95%（口径同 §8.2，单条下限提至 80%） |
| 累积失败样本 | ≥ 200 次 |

**决策点：用 200+ 次失败样本算出 triage 分类器的真实准确率，
再决定是否放开「执行错误自愈」。** §6.3 推迟自愈正是为了等这个数据 ——
有数据后决策才成立。

### 8.4 阶段 3：按需深化（持续，不设结束线）

`domain.md` / L2 详情层补完；报表图表启用视觉断言；新需求的 spec 由 Agent 起草、人 review。

验收看**新需求用例的采纳率**（Agent 起草被人接受的比例）。

**路径图谱放到这里都不一定要做** —— 后台是菜单驱动的树，`sitemap.md` 大概率一直够用。

### 8.5 明确不做（YAGNI）

视觉元素定位、路径图谱平台、周 Review 机制、L2 知识库前置建设、
独立 Skill 包分发、多机型矩阵。

理由统一：**要么被 Web DOM 取代，要么是规模化的产物而非前提。**
从零开始时建这些等于给自己造框架。

## 9. 风险与退出条件

### 9.1 风险清单

| # | 风险 | 影响 | 对策 | 是否已解决 |
|---|---|---|---|---|
| 1 | `sitemap.md` 路由表漂移 | Agent 基于过期地图生成用例 | CI 路由漂移检测（§4.4） | ✅ 页面增删可挡 |
| 2 | `domain.md` 语义腐化 | 业务知识过期，用例逻辑错 | 约定 + 定期人工过 | ❌ **未解决**，>100 条用例后重评是否合仓 |
| 3 | 固化脚本"假绿" | CI 全绿但断言的是错的东西 | 负向验证门槛（§6.2） | ✅ 新增用例可挡 |
| 4 | triage 误判把真 bug 当环境问题重试掉 | 漏 bug | 默认不自愈（§6.3） | ✅ 已规避 |
| 5 | 审核负担吃掉提效收益 | 工作从"点手机"变成"看 diff" | 阶段 2 量化工时降幅 | ⚠️ 需数据验证 |
| 6 | 深层造数依赖导致耗时与失败率上升 | 用例慢、偶发失败 | 依赖深度 >3 层即评估组合接口（§7.8） | ⚠️ 需后端配合 |
| 7 | 部分数据无 API、只能手工准备 | 无法自动化该类用例 | 阶段 0 盘点，需单独设计半自动预置策略 | ❌ **待澄清**（§11） |
| 8 | 单条生成成本高于人工写脚本 | 方案不经济 | 阶段 1 实测对比 | ⚠️ 需数据验证 |

### 9.2 退出条件（必须提前写进方案）

出现以下任一情形，判定该路径当前不可行并停止投入：

1. **阶段 1 结束通过率 < 80% 且根因是产品可测性**（而非脚本问题）
   → 先补可测性，方案本身推迟。
2. **单条用例生成成本 > 人工写脚本成本** → 直接人工写，不用 Agent。
3. **阶段 2 人工工时降幅 < 20%** → 审核负担已吃掉收益（风险 5 成真）。

**不写退出条件的方案，在数据不好时只会被不断加投入抢救。**

### 保留的原文档核心设计

以下部分完整继承，是方案的骨架：

- **三层架构 + 三条约束**（意图不可改、确定性 >95% 才固化、人只深度参与意图层）
- **Code-as-Action 而非 ToolCall** —— 可固化性、调试能力、表达力、成本四项占优
- **脚本固化 → 零 Token 回归** —— 整套方案的经济学基础
- **知识跟代码一起管理**（Git、review、分支、diff）
- **人定标准、Agent 执行探索** —— 组织原则
- **错误三分类**（环境 / 执行 / 用例）—— 保留分类，仅推迟自动化处置
